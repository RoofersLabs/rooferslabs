# Local development

Local development runs entirely on your machine. It touches **no AWS
resources** — no Terraform, no credentials, no VPN, no bastion.

| | |
|---|---|
| API | `http://localhost:4000` |
| Web | `http://localhost:5173` |
| Postgres | Docker, `localhost:5432` |
| Redis | Docker, `localhost:6379` |
| Clerk | your **Development** instance |
| Paddle | sandbox, or off |
| Launch gate | always disabled locally |

## Prerequisites

- **Node 22+** — `node -v`
- **Docker Desktop**, running — Postgres and Redis
- **Bun** (optional; npm works) — `curl -fsSL https://bun.sh/install | bash`
- **A Clerk Development instance** — the only credential you must supply

You do **not** need the AWS CLI, Terraform, or any AWS account.

## Installation

```bash
git clone git@github.com:RoofersLabs/rooferslabs.git
cd rooferslabs
bun install
bun run setup
```

`bun run setup` creates `.env` from `.env.example` and stops, asking for your
Clerk keys. Add them:

```
CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
```

> Clerk Dashboard → the **instance selector** (top left) → **Development** →
> API Keys. They must be `pk_test_`/`sk_test_`. Setup refuses to continue on a
> `pk_live_` key: those point at the live user directory, where your test
> sign-ups become real customer records.

Then re-run it:

```bash
bun run setup
```

It installs dependencies, starts Postgres and Redis, generates the Prisma
client, applies migrations, and validates everything. It is idempotent — re-run
it whenever you want.

## Running

```bash
bun run dev
```

Starts both servers, prints the URLs, and stops both on Ctrl-C.

| Command | |
|---|---|
| `bun run dev` | API + web together |
| `bun run dev:api` | API only |
| `bun run dev:web` | web only |
| `bun run check` | re-run the environment checks |
| `bun run db:up` / `db:down` | start / stop Postgres and Redis |
| `bun run db:migrate` | create and apply a migration |
| `bun run db:reset` | wipe and rebuild the local database |
| `bun run db:studio` | browse the database |
| `bun run typecheck` / `lint` / `test` / `build` | |

## Environment variables

Everything lives in `.env` (gitignored). `.env.example` is the annotated
template and the source of truth for what each value does.

Only these need your attention:

| Variable | Required? | |
|---|---|---|
| `CLERK_PUBLISHABLE_KEY` / `CLERK_SECRET_KEY` | **yes** | Development instance (`pk_test_`/`sk_test_`) |
| `OPENAI_API_KEY` | no | empty disables the AI receptionist |
| `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` | no | empty disables telephony — the safe default |
| `PADDLE_*` | no | only if `PAYMENTS_ENABLED=true`; must be sandbox |

`DATABASE_URL` and `REDIS_URL` already point at the Docker services and need no
edit.

> **The Clerk publishable key encodes the Frontend API host.** `pk_test_…`
> base64-decodes to `<slug>.clerk.accounts.dev`; `pk_live_…` decodes to
> `clerk.rooferslabs.com`. So the *key alone* decides where the browser fetches
> clerk-js from and which user directory it authenticates against — there is no
> `proxyUrl` or `domain` setting anywhere in this codebase, and nothing in the
> code will look wrong when it is wrong. `bun run check` decodes both keys and
> prints the host each resolves to; the web app refuses to boot on a `pk_live_`
> key outside a production build.

**`APP_ENV=development` is load-bearing.** It disables the private-beta launch
gate, selects the development service-worker cache namespace, and drives the
API's cross-environment guard — which refuses to boot production against
development infrastructure, and warns loudly in the other direction. It is
deliberately separate from `NODE_ENV`, which selects a *build* mode.

`apps/web/.env.local` is generated by setup from your `.env`. Delete it and
re-run setup to regenerate.

## Docker, Redis, and the database

`bun run setup` starts Postgres and Redis for you. Manually:

```bash
bun run db:up      # start
bun run db:down    # stop (data survives)
```

Data lives in a Docker volume and survives restarts. To start clean:

```bash
bun run db:reset   # drops, recreates, re-applies every migration
```

### Migrations

Author them locally against your own database:

```bash
bun run db:migrate      # prompts for a name, writes apps/api/prisma/migrations/
```

Write migrations **by hand** rather than with `prisma migrate diff` — it renders
column renames as data-destroying `DROP` + `ADD` pairs.

Production migrations apply automatically when the API container starts. There
is no local path that can reach the production database.

## Daily workflow

```bash
git pull
bun install          # only if package.json changed
bun run setup        # only if the schema or .env.example changed
bun run dev
```

Then `bun run typecheck && bun run lint && bun run test` before pushing.

Pushing to `develop` runs CI and deploys nothing. Production deploys from `main`
only — see `docs/environments.md`.

## Troubleshooting

**`bun run check` is the first thing to run.** It reports what is wrong and what
to type.

| Symptom | Cause and fix |
|---|---|
| `PostgreSQL is not reachable` | Docker is not running, or the containers are stopped. `bun run db:up` |
| `Redis is not reachable` | Same. `bun run db:up` |
| `Prisma client is not generated` | `bun run prisma:generate` |
| `Database is reachable but has no schema` | `bun run db:migrate` |
| `Clerk PRODUCTION keys in a local .env` | Switch the Clerk dashboard to its Development instance and copy `pk_test_`/`sk_test_` |
| `Web and API Clerk keys are different instances` | `bun run setup` re-syncs the web key from `.env` |
| Browser loads clerk-js from `clerk.rooferslabs.com` | A `pk_live_` key reached `apps/web/.env.local`. The publishable key **encodes** the Clerk Frontend API host — there is no proxy setting. `bun run setup` |
| `PAYMENTS_ENABLED=true but Paddle sandbox credentials are missing` | Set `PAYMENTS_ENABLED=false`, or supply sandbox keys |
| `EADDRINUSE :4000` or `:5173` | A previous run is still alive: `pkill -f 'nest start'; pkill -f vite` |
| Docker says "Cannot connect to the Docker daemon" | Start Docker Desktop and wait for **Running** |
| Type errors after pulling a schema change | `bun run prisma:generate` |
| `bun run dev` exits immediately | Preflight failed — run `bun run check` to see why |

### Things that are *not* problems

- **No AWS credentials.** Local development needs none.
- **`OPENAI_API_KEY is not set` warning.** The app runs; only the AI
  receptionist and call analysis are off.
- **`Twilio: telephony disabled`.** The intended default locally.

## What local development does not do

- It does not read Terraform state or AWS Secrets Manager.
- It does not reach the production database, cache, or API.
- It does not run the private-beta launch gate — that applies only to the
  production tier.

`infra/terraform/envs/development` provisions an optional shared development
database in AWS. Nothing in this workflow uses it, and it does not need to be
applied.
